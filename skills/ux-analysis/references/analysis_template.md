# 分析结论结构与写作指引

> 本文件为用户研究分析结论技能的参考模块，在Step 6生成Word分析结论时读取使用。

## 排版格式规范（强制执行，保证可视化质量）

> 所有分析结论输出均须遵守以下格式约束，避免"内容堆叠、层级不清"。由 `scripts/analysis_builder.py` 渲染时，对应块类型已内置这些格式；无 Python（P3/P4）降级输出时按同等规范手工排版。

### 1. 标题与副标题

- 文档主标题为研究主题（如"金融领域AI智能化产品用户需求研究分析结论"）。
- **副标题只保留两个内容**：生成日期 + 方案类型，格式固定为 `生成日期：YYYY-MM-DD ｜ 方案类型`（如"生成日期：2026-08-17 ｜ 方案A：客群主轴式"），居中对齐、灰色小字。
- **副标题不得包含任何数据相关内容**（样本量、数据源、研究方法、N=XX、受访者人数等）——这些一律移入正文"研究概述"。数据情况若放副标题，会显得杂乱且不专业。
- 对应 `analysis.json` 的 `"subtitle"` 字段：只需 `生成日期：… ｜ 方案：…`，不要在 subtitle 里追加"数据来源：…""N=…""方法：…"等内容。

### 2. 正文段首空两格

- 正文段落（paragraph）一律**首行缩进 2 个字符**（中文排版规范），不缩进仅适用于：标题（含副标题）、表格、图表、项目符号列表项、图注等非正文段。

### 3. 核心结论的段落格式（每条结论固定三段式）

每条核心结论使用 `conclusion` 块，格式固定为：

| 组成部分 | 格式 | 说明 |
|---------|------|------|
| 一句话结论 | **加粗，单独一段，无项目符号，段首空两格** | 最重要，放最前（金字塔结构） |
| 关键数据 | **每条单独一段，段首加项目符号，取消悬挂缩进（正文缩进内起行）** | 取 1-3 条最有说服力的数字/用户原声，来源与样本量标注在括号内 |
| 结论可信度 + 原因解读 | **合并为同一段，无项目符号，段首空两格；结论可信度在前，原因解读在后，以"。"衔接** | 结论可信度：高 / 中高 / 中 / 中低 / 低（五级定档见 `references/synthesis.md`；仅单源时永不为"高"，证据不足追加标注"证据有限"）。原因解读为推断性内容，标注"本研究认为" |

> **关键数据不悬挂缩进**：关键数据虽带项目符号，但**不做悬挂缩进**（负首行缩进），在正文段首缩进（2 字符）基础上起行，避免立体的悬挂对齐导致版面过度缩进。

示例（`analysis.json` 中一条结论的写法）：

```json
{"type": "conclusion",
 "statement": "注册流程是当前满意度最低、流失最高的关键环节，建议优先优化。",
 "data": [
   "该功能满意度均值 2.8/5，显著低于登录（3.5/5）（问卷 N=156）；",
   "注册至首次转账的转化率仅 52%（埋点 2026-01~02）；",
   "\"注册要填的信息太多，好几次想放弃\"（受访者 P03）。"
 ],
 "confidence": "结论可信度：高（问卷 + 埋点 + 访谈多源收敛）",
 "interpretation": "本研究认为，高流失主要源于信息采集门槛，而非功能故障。"}
```

渲染结果：一句话结论加粗单独一段 → 关键数据逐条加项目符号（无悬挂缩进）→ 末段"结论可信度：高（…）；本研究认为，高流失主要源于信息采集门槛，而非功能故障。"。

### 4. 行动建议的展示方式

- 行动建议**优先用 bullets 逐条分段展示**（每条单独一段、带项目符号），不采用表格；当且仅当建议条目少（≤3 条）且每条只有一个维度（如"建议+优先级"两列）时，才可考虑表格。
- 每条建议内容较多（含"建议 + 支撑要点 + 预期影响"三段式）时，一律按条分段书写，**禁止塞进表格单元格**。
- 优先级用【高优先级】【中优先级】【低优先级】【待验证】前缀标注，可读性优先。

### 5. 图表与表格

- 图表居中插入，带编号图注（"图1 …"）居中显示；
- 表格居中，表头加粗、底色浅灰；
- 图注/表注字号小于正文（9pt），灰色。

## 分析结论结构（半结构化 · 按需组合）

> **术语分离原则**：Step 4 聚类产生的"主题"及"聚类、三角验证、编码、L1/L2/L3"等均为**内部工作术语**，只在分析过程与 Step 5 用户审查时使用，**绝不直接出现在分析结论正文中**。进入分析结论时，直接用主题名作为章节标题（如"注册流程门槛较高"），并转化为面向读者的自然表述。

> **半结构化原则**：分析结论不强求统一固定章节，由"必选模块 + 可选模块"按需组合。先判断"读者最需要带走、并能据此做决策的核心结论是什么"，再组织模块；只保留支撑核心结论的内容，详略随研究类型与数据情况调整，不强制附录。

### 多类型综合分析结论的组织方式

一次研究含多种研究类型（如竞品分析 + 体验评估、客群研究 + 用户需求分析）时，分析结论按以下两种方式之一组织：

**融合式（推荐）**：多类型共享同一份"核心结论"，各类型的结论按主题聚类后整合呈现；研究类型仅决定分析覆盖面。适合关联紧密、共同支撑一个决策的类型组合。
- 示例：竞品分析 + 体验评估 → 核心结论中"竞品功能优势"与"自身体验短板"相互呼应，交叉点（"竞品的机会点是否对应自身痛点"）作为综合结论给出。

**分块式**：各类型相对独立时，分析结论按类型分块，每块一个小模块（研究概述可共享），最后统一给出行动建议。
- 示例：客群研究 + 用户需求分析 → 先呈现"客群画像"，再呈现"需求清单"，需求建议以画像为受众底座。

**选择依据**：若各类型的结论能在主题层面互相印证/组合成一个决策链条 → 融合式；若各类型回答的问题彼此独立、读者需分开阅读 → 分块式。拿不准时询问用户偏好。

### 必选模块（每份分析结论都应包含，详略可调）

**1. 研究概述**
- 研究背景与目的：1-2 句说明为什么做、要回答什么
- 方法：一句话说明采用的方法（如“本次研究采用了问卷及访谈的研究方法”）
- 样本：说明样本总量及参与者在重要特征方面的分布情况（如"156人参与问卷调研，12人参与访谈"），参与者分布可通过表格形式呈现

**2. 核心结论（全篇重点）**
- 若干条核心结论，每条一小节，标题直接用主题名
- 所有结论的排列要注意逻辑排序，描述整体的放在前面，描述部分的放在后面
- 每条结论用 `conclusion` 块，固定三段式（一句话结论加粗 / 关键数据逐条带项目符号无悬挂缩进 / 结论可信度与原因解读合并段），格式见"排版格式规范 §3"
- 数据来源直接写在数据后的括号里，不单独开"证据来源"专章


**3. 行动建议（优先级清单）**
- 按优先级排序；每条建议给出：建议 + 支撑要点 + 预期影响
- **展示方式**：默认 bullets 逐条分段展示（不用表格，见"排版格式规范 §3"）
- 证据不够充分的建议标注"[待验证]"并给出验证方式

### 可选模块（按需增删，不强制）

| 模块 | 适用时机 |
|------|---------|
| 对比矩阵 | 竞品分析、设计方案对比验证类（核心载体） |
| 问题清单 | 可用性评估、用户声音分析、访谈、开放题等产出具体产品问题时采用 |
| 分维度详表 | 需多维对比支撑结论时（如 ETS 8 维度、功能矩阵） |
| 图表 | 为核心结论提供可视化（满意度对比、漏斗、雷达等） |
| 嵌入框架产出 | Step 4 产出的结构化框架：卡诺矩阵 / 画像卡 / 旅程图 / 服务蓝图 / 心智模型图 / JTBD 动机映射表（定义与执行见 `references/frameworks.md`） |
| 数据间说明 | 仅当存在显著可能导致误判的数据矛盾且需说明时，作为对应结论小节内的一句话补充，不作为独立章节 |
| 方法细则扩充 | 需严谨交代执行方式、样本细节时 |

> **问题清单呈现规范**：开放题/用户声音反馈处理遵循"先融合、后列表"原则。**有量化对应时优先融入**：开放题问题能对应到 ETS 维度或功能分析时，作为佐证直接融入对应 ETS 结论（关键数据 + 原因解读），不单独成章；**完整问题清单作支撑**：产出具体问题时，在章节末尾或独立小节以**表格形式**完整罗列，表头建议为「问题描述 / 提及条数（或频次）/ 涉及功能或维度」，按提及条数降序排列，列表前用一句话说明来源与已融入章节；无量化对应的抽象主题/态度则按普通主题用 `conclusion` 块呈现。

> 无"附录"章节。如需交付原始统计，另行单独提供数据文件，不写入分析结论。

## 按研究类型的核心内容建议（可选起点）

> 研究类型在 Step 1 由技能从研究目的自动提炼、经用户确认（见 `references/research_types.md`）。下表列出各类型通常应覆盖的**核心结论内容点**，作为组织"核心结论"与"可选模块"的起点；可按实际情况裁剪、增删、调整顺序，不必每项都写，也不必按固定编号。含多类型时，各类型的内容点合并后去重，再按融合式或分块式组织。

### 客群研究

- 核心结论覆盖：客群画像要点、关键行为习惯与态度偏好、场景下需求与痛点、对产品服务的机会点
- 常用可选模块：客群画像卡片 / 图表

### 用户需求分析

- 核心结论覆盖：关键习惯与态度、背后的深层原因（动机：功能 / 情感 / 社会）、需求清单与分类、对设计与运营的建议
- 常用可选模块：需求清单表格；深层动机类研究可用 JTBD 动机映射表（任务 / 情境 / 三维动机 / 任务阶段 / 结果期望 / 现状方案 / 机会点，见 `references/frameworks.md`）

### 竞品分析

- 核心结论覆盖：定位差异、功能差异、客群差异、发展趋势与机会点、借鉴建议
- 常用可选模块：对比矩阵（必用）

### 需求分析

- 核心结论覆盖：需求类型分布（卡诺）、重要性评估、建设改造优先级
- 常用可选模块：优先级表格

### 功能架构设计

- 核心结论覆盖：用户自然分类习惯、命名/分组的调整点、建议架构与现状差异
- 常用可选模块：架构示意 / 差异对比表

### 设计方案对比验证

- 核心结论覆盖：分维度对比结论、偏好结果与内在原因、推荐方案（含是否符合需求）
- 常用可选模块：对比矩阵（必用）

### 体验测试

- 核心结论覆盖：整体体验水平、问题清单与严重程度、上线预备度结论
- 常用可选模块：指标详表 / 图表

### 体验评估

- 核心结论覆盖：整体水平（ETS-U、ETS-E）、分维度表现、典型问题、改进建议
- 常用可选模块：雷达图 / 分维度详表

#### ETS 系列结果输出层级规范（强制）

ETS 类评估（ETS-U / ETS-E，含传统 ETS 与 ETS.AI 指标体系）的结果输出必须遵循以下层级，避免主维度与特征指标混排、顺序颠倒：

**1. 层级原则（什么是"级"，什么是"类"）**

- **主维度**：指标体系的一级分组。传统 ETS 为 8 个主维度（功能流程、信息认知、交互设计、系统性能、安全感知、视觉设计、智能化、运营服务）；ETS.AI 为 4 个主维度（交互设计、多模态融合、安全效能、认知联接）。
- **特征指标**：主维度下的二级指标。传统 ETS 为 26 个特征指标、ETS.AI 为 14 个特征指标（如"输出内容准确度"属于"认知联接"、"意图识别精准度"属于"交互设计"）。
- **硬性约束**：特征指标必须置于其所属主维度的章节内展开，不得与主维度平级或单独成节。

**2. 顺序原则（引子先行）**

核心结论按以下顺序组织：

```
2.1 整体体验水平（ETS 得分、等级、NPS）
2.2 分维度总览与体验优化矩阵（引子：雷达图 / 14 或 26 指标图 / 满意度×关注度矩阵）
2.3 主维度 A：…（章节内展开其特征指标表现）
2.4 主维度 B：…
…（依此类推，覆盖全部主维度）
N.  分群差异 / 开放题诉求清单 / 行动建议
```

- 分维度总览与体验优化矩阵作为**引子**，置于整体体验结论之后、各主维度展开之前，用于引出后续逐维度分析。
- 各主维度结论中可引入开放题诉求作互证；开放题完整清单统一放在维度结论之后，标注「主维度/特征指标」双层级归属。
- 行动建议按主维度归类并标注优先级（如「【高优先级·认知联接】」）。

**3. 迷你结构样例（ETS.AI 示例）**

```
2.1 工小智整体体验处于「可用」级别，用户推荐意愿低迷
2.2 分维度总览与体验优化矩阵（引子）
2.3 交互设计维度：操作控制与视觉设计为优势项，意图识别是关注重点
2.4 多模态融合维度：输入与输出形态获认可，跨渠道协同偏弱
2.5 安全效能维度：客观公平获认可，响应速度与隐私信任存缺口
2.6 认知联接维度：回答质量与情境理解是最大短板
2.7 分群差异：低频、年轻、未使用用户评价更消极
```

> **生成**：将选定模块与内容翻译为 `scripts/analysis_builder.py` 的 JSON 块序列（heading + paragraph/bullets/table/chart），按实际结构写入 analysis.json 即可，无需为各研究类型定制代码。

## 写作指引

### 研究概述（精简）

- 背景 1-2 句 + 目标一句
- 方法 + 样本一句话
- 写法示例："本次研究采用混合方法设计，问卷 N=156 进行满意度量化评估，访谈 N=12 挖掘深层需求与痛点。"

### 核心结论

**每条结论的结构**（格式见上方"排版格式规范 §3"，用 `conclusion` 块渲染）：

- **一句话结论**：加粗、单独一段、无项目符号（如"注册流程门槛最高，为所有功能中最低"）
- **关键数据**：逐条单独一段、带项目符号、无悬挂缩进，取 1-3 条最有说服力的数字，标注来源与样本量（如"满意度均值 2.8/5；问卷 N=156；访谈 4 人提及困惑；埋点错误率 35%"）
- **结论可信度 + 原因解读**（合并为同一段，结论可信度在前、原因解读在后，以"；"衔接）：结论可信度用 **高 / 中高 / 中 / 中低 / 低** 五级定档（规则见 `references/synthesis.md`）；单源结论永不为"高"，证据不足时追加标注"证据有限"。原因解读为推断性内容、标注"本研究认为"


**写作原则**：

- 先整体后部分
- 先总后分
- 先结论、后证据，金字塔结构
- 数据必标来源与样本量
- 引用保留原始措辞，标注受访者编号
- 不写没有数据支撑的断言
- 不使用内部术语（主题、聚类、三角验证、编码、L1/L2/L3），转为面向读者的自然表述
- **只保留支撑核心结论的内容**；与结论无关、不影响判断的细节一律省略

### 行动建议

- 每条建议：建议内容 + 支撑要点 + 预期影响
- **展示方式**：默认用 bullets 逐条分段展示（每条单独一段带项目符号），不采用表格（见"排版格式规范 §3"）；仅建议极少且为简单两列时可考虑表格
- 每条建议加优先级前缀：【高优先级】【中优先级】【低优先级】【待验证】
- 按优先级排序
- 证据不足的建议标注"[待验证]"并给出验证方式：证据不足补数据、可快速验证用 A/B 测试、需长期观察用埋点监测

| 眼动-A/B对比 | 并列热区图或分组条形图 | 不同版本视觉注意力差异 |
| ETS 8维度 | 雷达图 | 各维度满意度分布 |
| 体验优化矩阵（满意度×关注度） | 散点图 | 各维度四象限，定位优先改进区 |

## 写作风格

- 客观陈述，避免主观评价词（不说"很糟糕"，说"满意度均值为2.1/5，低于行业基准3.5"）
- 结论先行：先给结论，再给解读，数字可以放在解读中
- 区分事实与推断：数据支撑的结论直接陈述；研究者推断加"本研究认为"或"结合XX数据推断"
- 受众意识：分析结论面向产品决策者，可以适当使用一些心理学术语提升专业度，避免过于学术化的表述，但保持专业严谨
- 一定要保证语句流畅通顺
