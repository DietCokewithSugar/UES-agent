# 用户声音数据分析引擎

> 本文件为用户研究分析结论技能的参考模块，在Step 3展示用户声音分析方案和Step 4执行用户声音分析时读取使用。同时，问卷中的开放题部分也使用本引擎的方法论。

## 适用条件

当Step 2识别到用户声音数据（客服对话/工单、App评论、社交媒体反馈、NPS原因文本、投诉/建议记录等非结构化用户原声文本）时激活。

也适用于：问卷中包含开放题时，开放题部分按本引擎方法分析。

## 数据特征

用户声音数据与访谈数据的本质区别：
- **访谈数据**：有研究设计引导，围绕预设问题展开，有追问深度
- **用户声音数据**：用户自发表达，无研究框架引导，主题分散但真实度高

这意味着用户声音分析需要更强的主题归纳能力，同时要警惕噪声（情绪发泄、无关内容）。

## 核心处理流程：标准四步法（S1–S4）

用户声音数据量大、单条信息量少且表述口语化，采用"规范化表述 → 语义分组 → 组内概括 → 典型问题合并"四步递进处理，逐层去噪提纯，最终收敛为稳定的典型问题清单。**这是本引擎的主干流程**，适用于客服工单、投诉、评论、NPS原因等各类用户声音。

> **执行说明**：四步对同一批用户声音串行执行（S1→S2→S3→S4），每一步的输出作为下一步输入；多条声音统一处理，不逐条孤立分析。

### S1 文本规范表述

**角色**：金融银行领域（如工行）的用户体验分析专家，擅长将用户意见反馈规范化表述。

**任务**：对输入的每条原始用户声音逐条处理，提炼生成规范的中文陈述句。

**要素提取**：规范表述仅包含两部分——**核心业务场景** + **异常现象或客户不满问题**，结构为"核心业务场景 + 异常现象或客户不满问题"（如"短信服务 不能接收动账通知"）。
- 核心业务场景 = 问题或异常的发生位置；
- 异常现象或客户不满问题 = 描述本身，不需重复业务场景。

**去噪处理**：
- 过滤主观情绪（如"气死了""垃圾"）
- 过滤冗余动作（如"重启手机""打客服"）
- 过滤语气词
- 忽略不改变问题本质的细节（日期、机型、系统版本、具体金额、网点名称等）

**统一表述**：口语转为简洁统一的书面专业词汇（如"钱没过去"→"到账延迟 / 交易失败"）。

**信息无损**：保留关键信息，如报错提示、关键操作节点等。

**颗粒度控制**：整体以偏概括为准，不要过细。

**逐条处理**：对每条原始用户声音处理，不能跳过任何一条。

**输出格式**（严格）：
```
||| 用户声音 ID ||| 用户声音规范表述
```
- 用户声音 ID 沿用原始列表中的 ID；
- 每条规范表述按含义重新排序后输出。

### S2 文本语义分组

**角色**：擅长对银行用户意见进行语义分类的专家，能精准识别用户意见背后的业务问题本质。

**任务**：对"用户声音规范表述"按所反映的问题内容进行分组。

**深度理解**：逐一理解每条规范表述的核心语义与隐含意图，识别关键实体、动作、情感倾向和领域归属，特别是涉及的银行业务场景、问题症状和异常现象主体。

**分组维度**（系统化比对）：
1. 语义等价性：核心命题是否相同
2. 词汇重叠度：表面词汇的 Jaccard 相似度
3. 结构相似性：句式结构与逻辑组织
4. 意图一致性：文本背后的用户意图是否一致
5. 上下文兼容性：是否可能在相同对话场景中出现

**忽略干扰**：忽略不改变问题本质的细节——日期、机型、系统版本、具体金额、网点名称、细节场景、客户具体状态、问题对客户的个体化影响、客户个性化表述（不同客户对相同问题表述差异大，分组时忽略个性化表述）。

**颗粒度控制（非常重要）**：分组颗粒度偏概括，相似业务场景、相关的异常现象主体尽可能归入同一组；**绝对避免产出过多语义相近的碎片化小组**。

**独立组处理**：只有与任何其他声音所反映问题都完全无关的孤立声音才独立成组。

**唯一性原则**：每条声音仅归入一个最相关的组；若涉及多个维度，按"第一痛点"或"最直接原因"判定。

**分组标记**：同一组每条声音标记同一组别号；不同组用不同正整数，组别号为从 1 开始的正整数。

**输出格式**（严格，禁止解释说明）：
```
||| 用户声音 ID ||| 用户声音规范表述 ||| 组别号
```
按组别号从小到大排列。

### S3 组内文本概括（典型问题提炼）

**角色**：处理金融银行领域用户反馈意见的专家，擅长归纳转述用户声音。

**任务**：按组别号依次归纳组内所有"用户声音规范表述"的共性问题，提炼成一条**典型问题描述**，一条对应一个组；并将该典型问题描述标注回组内每条用户声音。

**要求**：
1. 按第三列组别号依次对各组处理，不遗漏任一组；
2. 在每个分组内，准确理解共同反映的异常现象或问题、涉及的业务功能、关键场景要素；
3. 典型问题描述不是组内语句的简单拼接或摘要，而是重新概括和表述的结果；
4. 必须是完整、准确、自然的中文语句，规范使用标点，语句中不出现空格，不频繁使用"且"等拼接感强的词汇；
5. 表述清晰、准确，非技术人员也能理解，但不过多创造发挥；
6. 同一组别号下所有声音的典型问题描述字段必须**完全一致**；
7. **绝对禁止修改组别号**，严格遵照传入的组别号归纳，禁止遗漏；
8. 必须对每条用户声音 ID 标注典型问题描述和组别号。

**输出格式**（严格，禁止解释说明）：
```
||| 用户声音 ID ||| 典型问题描述 ||| 组别号
```
按组别号从小到大排列。

### S4 典型问题合并（与已有典型问题清单归并）

**角色**：银行业务领域经验丰富的文字总结归纳专家。

**任务**：以"已有典型问题列表（种子库）"为基础，比对"新的典型问题列表（待合并）"，生成合并后典型问题列表。

**核心逻辑**：
- 遍历新的典型问题列表中每一条，判断它是否可被已有典型问题覆盖；
- 可覆盖 → 在已有典型问题后标记覆盖的新问题 ID；
- 不可覆盖 → 将该条新典型问题追加补充到已有列表末尾。

**比对维度**（与 S2 分组维度一致）：语义等价性 / 词汇重叠度（Jaccard）/ 结构相似性 / 意图一致性 / 上下文兼容性。

**规则**：
1. 不可修改任何典型问题 ID 及描述的原文内容；
2. 初始化：所有已有典型问题作为输出列表基础，其"覆盖的新问题 ID 列表"初始为空；
3. 遍历/对应/追加：
   - 每条新典型问题逐个与所有已有典型问题比对；
   - 若某条已有典型问题可覆盖该新问题 → 将新问题 ID 填入该已有问题的"覆盖的新问题 ID 列表"（**每个新问题只能对应一个已有典型问题**，绝不可对应多个）;
   - 若某条新典型问题与所有已有典型问题均不相似 → 作为新行追加到输出列表末尾，ID 与描述保持不变，覆盖列表为空；
   - 新问题已对应到已有典型问题时，禁止再重复列出。
4. 输出必须包含所有已有典型问题，禁止遗漏。

**输出格式**（严格，禁止解释说明）：
```
||| 典型问题 ID ||| 典型问题描述 ||| 覆盖的新问题 ID 列表
```
- 覆盖的新问题 ID 列表用英文逗号分隔；无覆盖时为空。

> **S4 使用提示**：若本次分析是首次建立用户声音问题库，S4 以空种子库运行（全部新问题追加为初始清单）；若已有历史典型问题库，则按 S4 归并，输出会包含历史清单中未被新批次覆盖或覆盖到的完整状态。

## 分析方案（四步法基础上的扩展分析）

### 1. 数据清洗与预处理（S1前补齐）

**必做项**：
- 去除无效条目（空白、无意义内容如"好评""不错"、系统自动生成内容）
- 识别并标注情感极性（正面/负面/中性/混合，供情感-主题矩阵使用）
- 标注来源类型（客服/评论/投诉/NPS原因等）
- 如有元数据，提取用户分群信息（新/老用户、VIP、地区等）

**输出**：清洗后的有效数据集 + 基础统计（总条数、有效条数、来源分布、情感分布）

### 2. 典型问题频次统计（S4产出后）

对合并后的典型问题清单计算：
- 每个典型问题覆盖的声音条数及占比
- 每个典型问题的情感分布（负面占比高的优先改进）
- 每个典型问题按来源类型/用户群的分布（供第4步交叉使用）

**输出**：按条数排序的典型问题清单（Top N）+ 各问题情感/分群明细

### 3. 情感-主题矩阵

将情感分析与典型问题交叉：

| 典型问题 | 正面 | 负面 | 中性/混合 | 合计 |
|------|------|------|----------|------|
| 问题A | XX条 | XX条 | XX条 | XX条 |
| ... | ... | ... | ... | ... |

**重点识别**：
- 高负面占比问题 → 优先改进方向
- 高正面占比问题 → 可强化优势
- 情感混合问题 → 需细分场景理解差异原因

### 4. 用户分群交叉（如有分群数据）

- 各典型问题在不同用户群中的分布差异
- 特定群体的独特关注点
- 高价值用户 vs 普通用户的声音差异

### 5. 与结构化数据交叉印证

当用户声音与其他数据源共存时：
- 用户声音典型问题 ↔ 问卷维度得分：声音中的痛点是否对应量表的低分项？
- 用户声音典型问题 ↔ 访谈发现：自发声音与引导回答是否一致？
- 用户声音典型问题 ↔ 埋点行为：用户说的和实际做的是否一致？（言行矛盾检测）

**关键价值**：用户声音是"无框架"的真实表达，与"有框架"的研究数据交叉时，能发现研究盲区和验证结论的生态效度。

### 6. 典型引用提取

为每个典型问题提取代表性引用：
- 选择最生动、最具体的原声（避免选择模糊笼统的条目）
- 每个典型问题2-5条典型引用
- 标注来源类型和情感极性
- 引用保留原始措辞，不做改写

## 问卷开放题的特殊处理

当分析对象是问卷中的开放题时，做以下适配：

1. **编码粒度**：问卷开放题通常较短，规范表述以完整条目为单位而非拆分语义片段（S1 可直接复用）
2. **与量表交叉**：开放题典型问题必须与同一问卷的量表发现对照——量表某维度低分时，检查开放题是否有对应的具体原因描述
3. **分群交叉**：结合问卷的人口统计和分群变量，看不同群体的开放题典型问题差异
4. **引用标注**：使用问卷编号（如R156），不用P编号
5. **呈现形式**：开放题处理遵循"先融合、后列表"原则——**有量化对应时优先融入**：开放题问题能对应到 ETS 维度或功能分析时，作为佐证直接融入对应 ETS 结论（关键数据 + 原因解读），不单独成章；**完整问题清单作支撑**：产出具体问题时，在章节末尾或独立小节以**问题列表（表格）**完整罗列（表头「问题描述 / 提及条数 / 涉及功能或维度」，按提及条数降序，前附一句话来源说明与已融入章节）；无量化对应的抽象主题/态度则按普通主题用 `conclusion` 块呈现。具体规范见 `references/analysis_template.md` 的"问题清单"模块。

## 与访谈分析引擎的区别

| 维度 | 访谈分析（interview.md） | 用户声音分析（本文件） |
|------|------------------------|---------------------|
| 数据来源 | 研究者引导的深度对话 | 用户自发表达 |
| 分析深度 | Braun & Clarke完整六阶段 | S1–S4 四步标准化流程 + 情感矩阵 |
| 编码粒度 | 细粒度语义片段 | 以条目为单位 |
| 特有分析 | 编码本 + 框架分析备选 | 标准四步法（规范表述→分组→概括→合并）+ 情感-主题矩阵 |
| 核心价值 | 深度理解原因和动机 | 捕捉自发真实声音和趋势 |
