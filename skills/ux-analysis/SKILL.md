# 用户研究分析结论

引导用户从原始研究数据出发，经过分析、洞察提炼、主题聚类，最终生成专业Word格式的分析结论，作为研究人员撰写正式研究报告时的结论参考。

## 核心原则

- **按研究主题组织**，不按数据源罗列——这是本技能的核心差异化价值
- **引导式交互**，每一步都让用户参与确认，非专业用户也能理解"为什么得出这个结论"
- **三角验证**，自动检测多源收敛与言行矛盾
- **支持单数据源和多数据源**，单数据源时自动弱化跨源综合步骤

## 用户交互节点总览

本技能全程鼓励用户参与确认（引导式交互），其中step1、step3、step5必须有用户确认环节。所有需要用户决策/确认的节点，**都必须同时给出参考选项并允许开放式答复**——提问时先列 2~4 个推荐选项（数字编号 ① ② ③），随后注明"以上都不是也可以直接说明"；不得只给封闭选项，也不得只抛开放式问题不给出参考。

| # | 交互节点 | 触发时机 | 参考选项示例 | 允许开放答复 |
|---|---------|---------|------------|------------|
| 1 | 研究背景录入 | Step 1 基本信息收集后 | 研究目的模糊时：① 让我追问每一条目的 ② 我补充背景材料 ③ 接受现状直接继续 | 是 |
| 2 | 研究类型确认 | Step 1 自动提炼类型后 | ① 确认上述类型 ② 增删类型 ③ 不确定，帮我解释各类型含义 | 是 |
| 3 | 数据清单确认 | Step 2 识别数据类型后 | ① 全部识别正确 ② 有标签要修改 ③ 有文件没被识别 | 是 |
| 4 | 眼动信息补充 | Step 2 识别到眼动数据后 | ① 逐项提供设计预期 ② 只有部分信息 ③ 无预期，看数据说话 | 是 |
| 5 | 框架充分性检查 | Step 3 框架数据不足时 | ① 降级为单源近似结论并标注 ② 从方案中移除该框架 ③ 补充数据后再产出 | 是 |
| 6 | 分析方案确认 | Step 3 方案预览后 | ① 方案OK，执行 ② 调整分析重点 ③ 增删分析步骤 | 是 |
| 7 | 言行矛盾解释 | Step 4 三角验证发现矛盾时（多源） | ① 按我的业务解释处理 ② 作为主题保留待验证 ③ 降级为单源标注 | 是 |
| 8 | 主题结构审查 | Step 5 主题列表展示后 | ① 结构OK ② 合并/拆分/重命名主题 ③ 增删主题 ④ 调整优先级 | 是 |
| 9 | 专业判断补充 | Step 5 审查时 | ① 接受现有洞察 ② 补充你的专业判断 ③ 修正某条洞察 | 是 |
| 10 | 洞察待验证标记 | Step 5 审查时 | ① 标记指定洞察为待验证 ② 本轮不标记 | 是 |

| 12 | 多类型组织方式 | Step 6 多研究类型时 | ① 融合式（共享核心结论） ② 分块式（每类型一个模块） | 是 |

> **提问格式规范**：每个节点用一句话说明当前状态 → 给出编号选项 → 明确"以上都不是也可以直接说明"。用户答复编号可视为选中该选项；答复正文按开放答复处理。研究材料已由 **ux-kit** 带入时，节点 1/2 的信息自动填充，只询问"是否确认"，不要重复追问。

> **交互硬性规则（必须遵守，本技能为分步交互式流程）**：
> 1. **每个节点必须先提问并停止输出**——向用户给出状态说明与参考选项后，**立即终止本轮输出**，等待用户答复后才能进入下一步。
> 2. **未收到用户答复前，禁止继续输出**任何分析内容、主题列表、洞察或最终结论文件；不得"自问自答"式替用户做选择。
> 3. 必须等待用户**明确确认**后才能进入下一节点；若用户提出修改意见，按修改更新后再请确认（参照 ux-kit 的确认节奏）。
> 4. 用户答复"以上都不是"或直接开放描述时，按其描述内容继续，同样先确认再前进。

## 工作流程

### Step 1：研究背景录入

向用户收集以下信息：

| 字段 | 必填 | 说明 |
|------|------|------|
| 研究产品/功能名 | 是 | 本次研究的产品或功能 |
| 研究类型 | 否（由技能自动提炼，用户确认） | 本次研究覆盖的研究类型（可多选）：客群研究 / 用户需求分析 / 竞品分析 / 需求分析 / 功能架构设计 / 设计方案对比验证 / 体验测试 / 体验评估（定义与自动匹配规则见 `references/research_types.md`） |
| 研究背景 | 是 | 为什么做这次研究 |
| 研究目的 | 是 | 本次研究要回答什么问题 |
| 研究方法 | 否 | 使用了哪些方法（可从前置研究方案Skill带入） |
| 样本设计 | 否 | 样本量、抽样方式 |
| 研究内容概述 | 否 | 研究覆盖的主题/模块 |
| 关键关注点 | 否 | 用户特别想深入了解的方向 |

如果用户是从研究材料产出 Skill（**ux-kit**）衔接过来的，上述信息应自动带入，用户只需确认或补充。若本次研究尚无可用的研究方案、访谈提纲、问卷等研究材料，可参照 **ux-kit** skill 产出研究材料（研究方案 / 访谈提纲 / 问卷 / 可用性测试方案 / 用户声音分析方案等），再回到本 Skill 进行数据分析与结论生成——研究材料的设计与采集由 ux-kit 负责，本 Skill 负责数据到手后的分析与结论产出。

**研究类型提炼**：本技能按研究类型组织分析结论（共 8 类）。研究类型**无需用户手动输入**——技能根据"研究目的/要回答的问题"（及关键关注点）自动匹配一个或多个类型，展示给用户确认或修正（如"我们的产品体验如何"→ 体验评估；"竞品有何借鉴"→ 竞品分析；"了解目标客群并挖掘深层需求"→ 客群研究 + 用户需求分析）。自动匹配的信号对照见 `references/research_types.md`。展示时按节点 2 提问：**① 确认上述类型 ② 增删类型 ③ 不确定，帮我解释各类型含义**（以上都不是也可以直接说明）。

**研究类型决定**：① Step 3 的分析焦点；② Step 4 的聚类主线；③ Step 6 的核心内容建议。**一次研究可包含多种研究类型**（如竞品分析 + 体验评估合出综合结论），此时类型集合代表分析覆盖面，分析结论按"融合式/分块式"组织（见 `references/analysis_template.md` 与 `references/research_types.md`）。

**关键约束**：研究目的是后续主题聚类的锚点——所有分析都要围绕研究目标收敛，不是无方向的数据挖掘。如果用户给的研究目的太模糊，主动追问帮助明确（见节点 1：给参考选项 + 允许开放答复）。

### Step 2：数据上传与识别

交互流程：
1. 告知用户文件命名指引（见下方），请用户按指引命名文件后上传
2. 用户上传一个或多个数据文件
3. 综合文件名声明 + 内容特征双重识别，判定每份数据的类型
4. 输出数据清单（类型标签 + 格式质量评估）
5. 用户可修正类型标签、补充说明——按节点 3 提问：**① 全部识别正确 ② 有标签要修改 ③ 有文件没被识别**（以上都不是也可以直接说明）

**文件命名指引**（推荐但不强制）：

上传前按 `数据类型_描述.扩展名` 格式命名文件，帮助Skill更准确识别数据类型：
- `问卷_满意度调查.xlsx` / `问卷_新用户注册体验.csv`
- `访谈_老用户深度访谈.txt` / `访谈_新用户逐字稿.docx` / `访谈_核心用户访谈记录.xlsx`
- `埋点_首页转化漏斗.xlsx` / `埋点_功能使用数据.csv`
- `可用性_转账任务测试.xlsx` / `可用性_注册流程问题清单.docx`
- `眼动_首页热区图.png` / `眼动_AOI注视数据.xlsx`
- `用户声音_客服工单.xlsx` / `用户声音_App评论.csv` / `用户声音_NPS原因.txt`

未按指引命名的文件，Skill仍会通过内容特征自动识别，但命名可显著提高识别准确率。

**数据类型识别规则**（文件名声明 + 内容特征双重判定）：

| 数据类型 | 文件名关键词 | 内容特征信号 |
|---------|------------|------------|
| 问卷 | 问卷/调查/survey | 结构化多行多列数据；含各类选择题（单选/多选/下拉）、Likert量表、NPS/CSAT、评分题、排序题、开放题等；一行一条作答 |
| 访谈 | 访谈/interview/逐字稿/转录 | 对话格式（Q:/A:、主持人:/用户:、采访者:/受访者:）；逐段叙述体；录音转录稿（口语化长文本）；Excel中的访谈记录表（行=受访者/问题，列为结构化字段） |
| 埋点 | 埋点/行为/数据/漏斗/转化 | 原始事件流（事件名+时间戳+用户ID）；已处理的聚合数据（DAU/MAU表、转化率表、功能使用率表、漏斗数据等）；任何已整理的用户行为统计 |
| 可用性评估 | 可用性/测试/评估/usability/任务 | 任务完成率/成功率数据；用户遇到的具体问题列表；SUS/SEQ/ASQ量表数据；观察笔记/测试记录；错误类型与频次统计 |
| 眼动 | 眼动/热区/AOI/注视/eyetracking | AOI/fixation/pupil列数据；热区图截图 |
| 用户声音 | 用户声音/评论/投诉/工单/反馈/VOC | 客服对话/工单记录；App商店评论；社交媒体反馈；NPS原因文本；投诉/建议记录；任何非结构化的用户原声文本 |

**识别优先级**：文件名声明 > 内容特征。当两者矛盾时，以文件名为准并提示用户确认。

**识别后——眼动数据专项信息收集**：当识别到眼动数据时，额外收集以下信息，用于后续热区与设计预期的对照分析：
1. 每个页面/任务的**设计预期焦点**：你希望用户首先看到/重点关注什么？
2. 页面上的**重要信息区域**和**关键操作区域**：哪些位置的信息/按钮对任务完成至关重要？

用户提供方式：简短文字描述即可（如"首页预期焦点是中间的转账入口，重要操作区域是底部导航栏"），无需精确坐标。

> **眼动信息收集交互**：逐项向用户收集时，按节点 4 给出参考选项——**① 我能逐页提供设计预期焦点与重要区域 ② 只能提供其中一部分 ③ 没有设计预期，基于数据客观反馈热区分布**；选 ② 时继续追问哪些页面/任务有预期、哪些没有。开放答复（直接文字描述预期焦点）同样接受。

### Step 3：分析方案预览

基于Step 1的研究目标、研究类型和Step 2识别的数据类型，生成详细分析方案供用户确认。

**分析焦点随研究类型调整**：先读取 `references/research_types.md` 中对应研究类型的"分析主线"与"综合侧重"（多类型时合并去重），确定本次分析的重点方向（如"需求分析"聚焦卡诺需求分类与优先级，"设计方案对比验证"聚焦方案×维度对比），再叠加数据类型引擎。

**嵌入框架判定**：按研究类型判定本次需要产出的结构化框架（客群/需求分析→用户画像；需求分析→卡诺模型；用户需求分析→JTBD 动机映射（深挖动机）；体验评估/竞品→灵犀旅程；竞品/体验测试→服务蓝图；功能架构→心智模型），读取 `references/frameworks.md`，将对应框架纳入分析方案并告知用户其数据依赖与是否需跨源综合。

> **框架数据充分性检查**：frameworks.md 中标注"需综合"的框架（用户画像、灵犀旅程、服务蓝图、心智模型、JTBD 动机映射）依赖跨源数据（访谈/行为/流程等）。**若本次数据源不足以支撑（如仅单源问卷），不要硬套框架产出**——告知用户缺哪类数据，按节点 5 提问：**① 降级为单源近似结论并标注 ② 从方案中移除该框架 ③ 建议用户补充数据后再产出**（以上都不是也可以直接说明）。卡诺模型一般单源（问卷双题）即可。具体数据依赖见 `references/frameworks.md` 对应章节与"使用约束"。

**按数据类型读取对应分析引擎**：
- 问卷数据 → 读取 `references/questionnaire.md`，展示问卷分析方案
- 访谈数据 → 读取 `references/interview.md`，展示访谈分析方案
- 埋点数据 → 读取 `references/analytics.md`，展示埋点分析方案
- 可用性评估数据 → 读取 `references/usability.md`，展示可用性分析方案
- 眼动数据 → 读取 `references/eyetracking.md`，展示眼动分析方案
- 用户声音数据 → 读取 `references/user_voice.md`，展示用户声音分析方案

**展示内容**：
1. 各数据类型将执行的具体分析步骤
2. 分析重点说明（如"问卷重点关注NPS和满意度交叉"）
3. 预期产出说明（每个分析步骤会得到什么）

用户可调整分析重点，确认后进入执行。提问方式（节点 6）：**① 方案 OK，执行 ② 调整分析重点 ③ 增删分析步骤**（以上都不是也可以直接说明）。

### Step 4：分析执行 + 主题聚类

**4.1 各数据源独立分析**

按确认的方案执行分析，每类数据产出"数据快照"（关键数字 + 关键发现）。

**4.2 跨数据源主题聚类**

读取 `references/synthesis.md`（执行跨源综合）与 `references/research_types.md`（按研究类型调整聚类主线）：
- 按研究类型确定聚类主线（多类型时合并各类型主线；如客群研究按"画像-习惯-需求-痛点"，竞品分析按"对比维度"，体验评估按"体验维度"）
- 将所有数据源的发现打散为独立数据点
- 按语义亲和力重新聚类（不按数据源分组）
- 自下而上生成跨源主题
- 优先围绕Step 1的研究目标聚类，同时允许出现"研究目标之外的新发现"

**4.2b 嵌入框架产出**

当 Step 3 判定本次需要产出结构化框架（卡诺/画像/灵犀旅程/服务蓝图/心智模型/JTBD 动机映射）时，读取 `references/frameworks.md` 执行对应框架的分析步骤（可先于主题聚类收集所需数据，再基于聚类/三角验证结果完成产出）。框架的产出进入 Step 6 作为分析结论可选模块；需跨源综合的框架在 4.2 与 4.3 之后完成，确保用到综合后的证据。

**4.3 三角验证**（仅多数据源时执行）

对每个主题进行跨源验证：
- ✅ 收敛：多源一致，置信度**高**（可升档中高↔高）
- ⚠️ 矛盾：言行不一致，置信度**低**，需进一步解释
- ❓ 单源：仅一个数据源支撑，按"单源口径"定档（高↔中高↔中↔中低↔低五档，永不为"高"）

> **可信度定档**：三角验证输出五级可信度（高 / 中高 / 中 / 中低 / 低）。多源结论通常为高/中高；单源结论按方向一致性与数据点数量落入中高/中/中低/低（单源永不为"高"）。定档规则与"单源口径"见 `references/synthesis.md`「结论可信度五级定档」。

> **矛盾处理交互**（节点 7）：发现 ⚠️ 矛盾主题时，把矛盾点及可能解释展示给用户，提问：**① 按你的业务解释处理 ② 保留为待验证主题，现场不再深挖 ③ 降级为单源标注**（以上都不是也可以直接说明）。这既借用用户业务判断，又避免过度推断。

**4.4 洞察分级**

| 级别 | 定义 |
|------|------|
| L1 事实发现 | 数据直接呈现的现象 |
| L2 深层洞察 | 现象背后的原因/模式 |
| L3 行动建议 | 基于洞察的具体改进方向 |

**单数据源适配**：仅一个数据源时，跳过三角验证和言行矛盾检测，主题聚类仍正常运行。

### Step 5：主题结构与洞察审查

向用户展示以下内容，供审查和调整：

1. **主题列表**及优先级（基于：与研究目标相关度 × 数据支撑强度 × 影响面）
2. **每个主题的支撑证据**：来自哪些数据源，关键数据点/引用
3. **言行矛盾点**（仅多数据源时）+ 可能解释
4. **洞察分级**（L1/L2/L3）

用户可操作：
- 调整主题结构（合并/拆分/重命名/增删）
- 修改优先级
- 补充专业判断
- 标记需要进一步验证的洞察

交互方式（结合节点 8/9/10，一次提问可合并多节点）：
- 展示主题列表后：**① 结构 OK，直接生成结论 ② 我要调整主题结构（合并/拆分/重命名/增删） ③ 调整优先级 ④ 补充/修正专业判断**（以上都不是也可以直接说明）
- 若用户选择调整，逐项确认修改内容后再回到确认。
- 标记待验证洞察：**① 指定某条洞察为待验证 ② 本轮不标记**（开放答复可直接指出洞察编号）。

**设计意图**：让用户参与洞察提炼，理解"为什么得出这个结论"，而非黑箱输出。

### Step 6：分析结论生成

读取 `references/analysis_template.md`（含必选/可选模块、多类型组织方式与按研究类型的核心内容建议），基于研究类型、确认的主题结构和洞察生成Word分析结论。

> **术语分离**："主题/聚类/三角验证/编码/L1/L2/L3"是内部工作术语（Step 4/5 与用户审查用），**分析结论正文不出现这些词**——章节标题直接用主题名（如"注册流程门槛较高"），三角验证结果转为"结论可信度：高/中/低"。

> **格式规范**：分析结论全文遵守 `references/analysis_template.md` 的"排版格式规范"——正文段首空两格；核心结论每条用 `conclusion` 块三段式（**一句话结论加粗单独成段**、关键数据逐条带项目符号**且取消悬挂缩进**、原因解读与结论可信度**合并为同一段且结论可信度在前**）；行动建议内容较多时用 bullets 逐条分段展示，不用表格。脚本 `scripts/analysis_builder.py` 对这些块类型已内置格式，无需手工排版。

> **开放题融合规则**：开放题/用户声音反馈的处理遵循"先融合、后列表"原则——①**有量化对应时优先融入**：开放题问题若能对应到 ETS 维度或功能分析（如某条开放题对应某低分维度/优化项），将其作为佐证直接融入对应 ETS 结论的关键数据与原因解读中，实现量化与定性互证，**不单独成章**；②**无量化对应的抽象主题/态度**才按普通主题用 `conclusion` 块呈现；③**完整问题清单作支撑**：开放题产出的是具体问题时，在章节末尾（或独立小节）以**问题列表（表格）**完整罗列（表头建议为「问题描述 / 提及条数 / 涉及功能或维度」，按提及条数降序排列），作为前文融合分析的支撑材料，配一句话说明指向已融入的章节。这样既提高结论融合度，又保留完整问题清单供查阅。

**分析结论结构**（半结构化，按需组合，详见 `references/analysis_template.md`）：
- **必选模块**：研究概述（精简）→ 核心结论（每条结论＝一句话结论 + 关键数据 + 结论可信度，标题直接用主题名）→ 行动建议（优先级清单）
- **可选模块**（按研究类型与需要增删）：对比矩阵 / 分维度详表 / 图表 / 数据间说明 / 方法细则 / **嵌入框架产出**（卡诺矩阵、画像卡、旅程图、服务蓝图、心智模型图、JTBD 动机映射表——由 Step 4 执行，见 `references/frameworks.md`）
- **多类型组合**：本次研究含多种研究类型时，分析结论可按"融合式"（多类型共享一份核心结论，按主题整合）或"分块式"（每类型一个模块，最后统一行动建议）组织（详见 `references/analysis_template.md`）。生成前按节点 12 向用户确认组织方式：**① 融合式（共享一份核心结论） ② 分块式（每类型一个模块）**（以上都不是也可以直接说明）。
- **不设附录**；如需交付原始统计，另行单独提供数据文件，不写入分析结论

**单数据源适配**：核心结论的可信度按 `references/synthesis.md` 的"单源口径"定档（最高中高，永不为"高"）；证据不足/样本极少时追加标注"证据有限"。不出现"数据间说明"模块。
**对比型结论适配**（竞品分析、设计方案对比验证）："对比矩阵"模块为必用，三角验证按 `references/synthesis.md` 的对比型规则执行（比较对象为不同产品/方案）。

**输出格式**：.docx 文件

> **副标题硬约束**：分析结论副标题**只允许两个内容**——生成日期 + 方案类型，格式固定为 `生成日期：YYYY-MM-DD ｜ 方案类型`（如"生成日期：2026-08-17 ｜ 方案A：客群主轴式"），居中对齐、灰色小字。**不得在副标题出现任何数据相关内容**（样本量、N=、数据来源、研究方法、受访者构成等），这些一律写进正文"研究概述"。对应 `analysis.json` 的 `"subtitle"` 字段只需这两项内容。

> **输出方式确认**（节点 11）：开始生成前按自动化检测结果向用户说明将采用哪一级输出（P1~P4），并提问：**① 就按这个级别输出 ② 先给我看结构样例 ③ 我指定要 Word 格式的具体处理**（如"有 Python，就用 P1"）——以上都不是也可以直接说明。异常环境（无 Python/无依赖）主动告知用户，避免生成失败才暴露。

**工具与库指引**：

本技能需产出专业 Word 分析结论。请优先使用已沉淀的辅助脚本 `scripts/analysis_builder.py` 生成，不要在每次分析中临时重写 python-docx / matplotlib 样板代码：

1. 先按 `references/analysis_template.md` 的章节结构，把确认后的主题与洞察整理为一个结构化 JSON（协议与可用块类型见 `scripts/analysis_builder.py` 文档与内置 `ANALYSIS_EXAMPLE`：`heading` / `paragraph` / `conclusion`（核心结论三段式）/ `bullets` / `table` / `chart` / `image` / `pagebreak`），图表只需把数据写入 chart spec，无需手绘图表。核心结论一律使用 `conclusion` 块，行动建议用 `bullets` 逐条展示。
2. 再执行：
   ```
   python scripts/analysis_builder.py analysis.json output.docx
   ```
   脚本会自动：按 spec 用 matplotlib 绘制图表（临时 PNG）→ 用 python-docx 组装各章节 → 输出 .docx。全文默认排版字体为微软雅黑。

**STEP 2 读取用户数据文件的库**：

| 文件类型 | 推荐库 |
|---------|--------|
| .xlsx / .csv | openpyxl 或 pandas |
| .docx（逐字稿/访谈记录） | python-docx |
| .doc / .txt 纯文本 | 标准 open 读取 |
| .pdf（含图片类报告） | pdfplumber / PyMuPDF |
| .png / .jpg（热区图等） | matplotlib（PIL）读取展示 |

> **中文编码提示**：国内问卷/调研平台导出的 .txt/.csv 常为 **GBK / GB2312 / GB18030** 编码（UTF-8 直接读取会出现乱码）。解析前先用 `encoding="gb18030"`（或 gbk）尝试读取并**转码保存为 UTF-8** 再进一步分析；若试过常见编码仍乱码，再考虑 UTF-8 / UTF-8-sig。同一问题也可能出现在 .csv 的 BOM 上（UTF-8-sig 带 BOM 时有异常字符）。

**图表选型**：按 `references/analysis_template.md` 的"可视化指引"表选择 chart spec 类型（bar / line / pie / scatter / funnel / radar）；眼动热区图、浏览轨迹图直接用 `image` 块插入眼动仪导出的原始截图，无需重绘。

> **JSON 语法提示**：analysis.json 为纯 JSON，**所有数值必须为 JSON 合法类型**——`figsize` 等数组字段用 `[7, 4]`（非 Python 元组 `(7, 4)`），否则 JSON 解析失败。

**运行依赖**：Python 3 + python-docx、matplotlib、openpyxl（如需解析 Excel）。**但这只是最高保真的路径，不是必须的**——无 Python 时按下方"输出优先级"降级，任何电脑都能产出分析结论。

**输出优先级（四级逐级降级，确保任何环境都能产出分析结论）**：

| 级别 | 环境条件 | 输出方式 | 依赖 |
|------|---------|---------|------|
| P1 | Python 可用 | 用 `scripts/analysis_builder.py` 生成 .docx（图表用 matplotlib） | python-docx / matplotlib / openpyxl |
| P2 | Python 可用但缺依赖 | 先 `pip install python-docx matplotlib openpyxl`，成功后再按 P1 | 同上 + 网络 |
| P3 | 无 Python 或无法安装依赖 | 按 `references/html_analysis.md` 输出**自包含 HTML 分析结论**（内嵌 SVG 手绘图表），零依赖，浏览器/Word 均可打开 | 无 |
| P4 | 以上均不可行 | 输出结构化 Markdown，告知用户可粘贴进 Word 或协作工具 | 无 |

**失败处理细则**：

1. 运行前先检查 `python --version` 或 `py --version`，据此选择输出级别。
2. P2 安装依赖失败（无网络/无权限）时，降到 P3，不要卡住。
3. `analysis_builder.py` 运行失败：先看错误输出——JSON 结构问题对照脚本内协议修正；编码问题统一保存为 UTF-8；仍失败则降到 P3/P4。
4. 单个图表失败不影响正文：跳过该图并在原位置标注"（图略：原因）"，保证分析结论主体完整。
5. Step 2 数据文件无法解析：明确告知用户该文件无法解析，并请求提供替代格式（如导出为 .csv）。

## 单数据源 vs 多数据源适配规则

| 步骤 | 多数据源 | 单数据源 |
|------|---------|---------|
| Step 2 识别 | 识别多个数据类型 | 识别一个数据类型 |
| Step 3 方案 | 展示各类型分析方案 | 只展示该类型的分析方案 |
| Step 4 分析 | 独立分析 + 跨源聚类 + 三角验证 | 独立分析 + 主题聚类（无跨源） |
| Step 5 审查 | 含言行矛盾点 | 无言行矛盾点 |
| Step 6 分析结论 | 完整结构（含多源证据链+矛盾专题） | 简化结构（单源分析结果+主题组织） |

**特殊场景**：当问卷中包含开放题时，开放题部分按用户声音方法（`references/user_voice.md`）分析，量表部分按问卷方法分析——同一文件内可能触发两种分析引擎，但最终在主题聚类阶段统一整合。

## 注意事项

- 分析结论中所有引用必须标注数据来源（如"问卷N=156"、"受访者P03"）
- 统计结论需标注样本量和显著性（如适用）
- 访谈引用需标注受访者编号，不使用真实姓名
- 分析结论全文必须进行隐私脱敏：不得出现可识别个人的信息（姓名、手机号、账号、身份证号、设备号、工作单位等），一律替换为编号（受访者编号、问卷编号）或匿名描述
- 涉及内部业务敏感数据时，按合规要求处理，不披露未经授权的经营数据
- 洞察区分"数据支撑的结论"和"研究者的推断"，后者需明确标注
- 行动建议需标注数据支撑强度和置信度

### ETS 分析规范（体验评估 / 体验测试必读）

- **识别到 ETS 题型必须按 ETS 公式计算并输出**：一旦识别到 ETS-U 三题结构（NPS + 满意/优化双多选）或 ETS-E 结构（满意度陈述 + 特征指标重要度），**必须**按 `references/questionnaire.md` 4.2/4.3 的完整公式计算 ETS 得分，并写入数据快照的"ETS得分"项。**不得**退回为普通 NPS（推荐者/中立/贬损者）＋多选题频次占比的统计方式作为最终结果——NPS 只作为 ETS 公式的输入（比例形式代入 Step 6），多选题频次仅用于体验优化矩阵与雷达图辅助。
- **NPS 以百分数呈现**：NPS 计算结果统一展示为百分比形式（如 NPS = 78.7%），分析结论中不出现小数比例（0.787）形式。
- **维度名称不可修改**：ETS 分析中维度/指标必须使用 `references/questionnaire.md` 定义的标准名称——传统 ETS 用 8 个维度（功能流程 / 信息认知 / 交互设计 / 视觉设计 / 安全感知 / 系统性能 / 智能化 / 运营服务），ETS.AI 用 4 个维度（交互设计 / 多模态融合 / 安全效能 / 认知联接）及其特征指标名称。不得改用问卷原文的选项措辞（如"页面布局""安全感受""智能推荐""营销活动"）或其他自定义名称，以保证与 ETS 体系及分析结论模板一致。
- **ETS 题目可能随用户/产品特征微调**：实际问卷中 ETS 相关题目的选项措辞、维度个数可能与 `questionnaire.md` 中的标准模板不完全一致（如增减维度、换措辞，或传统 ETS 与 ETS.AI 指标混用）。分析时**先整体理解题目语义**，再判断题型归属与维度对应关系，按"语义最接近的标准维度/特征指标"归入（传统 ETS 归入 8 维度，AI 场景归入 ETS.AI 4 维度与特征指标），并在数据快照中注明实际映射关系，不要机械按题目序号或原文硬套。
