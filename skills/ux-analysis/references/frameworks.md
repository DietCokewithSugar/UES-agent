# 嵌入技术与结构化产出框架

> 本文件为用户研究分析结论技能的参考模块，在 Step 3 判定需要产出的框架、Step 4 综合分析阶段执行时读取使用。
> 本文件对应研究方法/研究材料产出 skill（ux-kit）中的"嵌入技术/综合产出"层级，但**视角为分析侧**：研究材料产出侧定义"采集时怎么设计"（如卡诺双题嵌入问卷、旅程回溯嵌入访谈），本文件定义"数据到手后如何分析并产出结构化成果"。

## 定位

嵌入技术是**横切多数据源的结构化产出框架**：不隶属于任何单一数据源，把已有分析发现/数据重组为特定结构（卡诺矩阵、画像卡、旅程图、服务蓝图、心智模型图）。它们不是数据源引擎（questionnaire.md 等），也不等于跨源主题聚类（synthesis.md）——主题聚类回答"发现了什么"，嵌入框架回答"用什么结构呈现/验证发现"。

**激活时机**：由 Step 1 的研究类型驱动。Step 3 判定本次需要产出哪些框架，Step 4 综合阶段读取本文件执行。

**各框架与数据源、研究类型、分析结论可选模块的对应关系**：

| 嵌入技术 | 依附研究类型 | 主要数据依赖 | 是否需跨源综合 | 分析结论呈现（可选模块） |
|---------|------------|------------|--------------|--------------------|
| 卡诺模型 | 需求分析 | 问卷（卡诺双题）为主，可交叉分群 | 一般单源即可 | 卡诺矩阵 + 需求分类表 |
| 用户画像 | 客群研究 / 用户需求分析 | 访谈 + 问卷(+埋点) | **需要** | 画像卡 |
| 灵犀旅程 | 体验评估 / 竞品分析 | 访谈 + ETS + 行为 + 声音 | **需要** | 旅程图 + 优化建议 |
| 服务蓝图 | 竞品分析 / 体验测试（服务类产品） | 访谈 + 桌面研究 + 一线流程 | **需要** | 服务蓝图 + 断点清单 |
| 心智模型 | 功能架构设计 | 访谈（任务提取）+ 卡片分类 | **需要** | 心智模型图 + 架构差异 |
| JTBD 动机映射 | 用户需求分析 / 客群研究 | 访谈 + 问卷(+用户声音) | **需要** | JTBD 映射表 + 机会点清单 |

## 1. 卡诺模型

**定位**：嵌入问卷调查的需求分类框架，用于划分功能属性类别并给出建设优先级。

**激活条件**：研究类型为"需求分析"；信号——需求优先级、功能分类、先做什么、取舍。

**数据依赖**：问卷中的卡诺双题（每个功能 2 题：正向"若提供此功能您觉得如何"+ 反向"若不提供您觉得如何"），每题 5 点：非常满意 / 理所当然 / 无所谓 / 勉强接受 / 很不满意。

**分析步骤**：

1. 逐人逐功能，将双题回答对照 Kano 评价表映射为属性类别：基本型（M）、期望型（O）、兴奋型（A）、无差异（I）、反向（R）、可疑（Q）。
2. 统计每功能各属性占比，**占比最高者定为该功能属性**；若两种属性占比比较接近（众数不明确），改用下方 Better-Worse 阈值判别表识别需求类型。
3. 计算 Better-Worse 系数（**可选增强**：占比定类即可得初步结果，BW 用于判断属性影响程度，非必要动作）：
   - Better = (A + O) / (A + O + M + I)　（提供该功能能提升多少满意度，范围 0~1）
   - Worse = -(O + M) / (A + O + M + I)　（不提供该功能会损失多少满意度，范围 -1~0，取绝对值衡量下降程度）
   - 阈值判别表（属性占比接近/众数不明确时定类）：

     | 需求类型 | Better | \|Worse\| |
     |---------|--------|---------|
     | 必备型（M） | < 0.5 | > 0.5 |
     | 期望型（O） | > 0.5 | > 0.5 |
     | 魅力型（A） | > 0.5 | < 0.5 |
     | 无差异型（I） | < 0.5 | < 0.5 |
4. 绘制二维矩阵：横轴 Worse（必备程度）、纵轴 Better（惊喜程度），分为四象限：必备要素、期望要素、魅力要素、无差异要素。
5. 形成优先级：M 必须满足（缺失即不满意）；O 投入产出比最高；A 差异化竞争机会；I 谨慎投入。
6. 可交叉分群（按画像/客群/使用频率）看不同用户的需求属性差异。

**产出**：卡诺二维矩阵图 + 需求分类表（功能 / 属性 / 各属性占比 / Better / Worse / 建议优先级）。

**综合要求**：一般单源（问卷）即可完成；跨源用于交叉印证（如与访谈痛点、用户声音对照），非必需。样本可靠性要求（保证结果准确性）：若数据在访谈等场景下回收且筛选已考虑代表性，按实验法样本量 30 人以上即可；若通过大范围问卷回收，建议按问卷调研抽样要求保证大样本（参考：用户规模 1000 万级产品，抽样误差 3%、置信水平 90% 时有效样本约 751 人）。

## 2. 用户画像

**定位**：多源综合产出框架，将分散的用户数据收敛为若干有辨识度的代表性用户类型。

**激活条件**：研究类型为"客群研究 / 用户需求分析"；信号——目标客群特征、用户是谁、分群、画像。

**数据依赖**：访谈（建立行为假设与维度）+ 问卷（聚类验证）+ 可选埋点（行为佐证）。

**分析步骤**：

1. **假设画像维度**：从访谈数据中提取可能区分用户的维度——**行为和目标优先，人口学仅作辅助**。
2. **亲和图聚类**：将访谈发现按相似性分组，形成画像假设。
3. **量化验证**：用问卷数据做聚类分析（K-means / 层次聚类），验证画像假设是否在更大样本中成立。
4. **画像定型**：形成 3-5 个画像，每个画像包含：画像卡名称与代表性人物（虚构）、关键特征、使用目标、行为习惯、痛点、典型引语、技能水平。

**产出**：画像卡（每个画像约 1 页）。

**综合要求**：**需要综合**（访谈定性 + 问卷定量）；画像的分群结论可反向支撑卡诺、旅程、心智模型的交叉分析。

> **待打磨（暂不实现）**：目前画像维度假设固定从访谈数据亲和图聚类中提炼（探索式路径）。后续可按需增补**验证式路径**——研究者基于桌面研究自行提炼区分维度后直接输入（维度名/定义/分层/问卷对应字段），技能结构化后直接做量化验证，仅在"维度来源"一步分叉，量化验证与画像定型共用现有逻辑。此属高阶方法，当前不改动现有流程。

## 3. 灵犀旅程（UDS，User Journey for Demand Pain Points Analysis）

**定位**：多源综合产出框架（来源：ICBC 中国工商银行业务研发中心）。通过"旅程结构 + 驱动因素 + 体验指标 + 典型问题 + 优化点"五要素，定位关键旅程环节并给出可量化的优化方案。

**激活条件**：研究类型为"体验评估 / 竞品分析（产品优化）"；信号——旅程、触点、端到端、全过程、体验地图、需求痛点。前置条件：产品有明确用户 + 明确交互流程。

**数据依赖**：访谈（驱动因素与典型问题的主要来源，8-20 人）+ ETS 评估（主观态度指标）+ 行为/交易数据（操作时间、转化率、交易量）+ 用户声音（投诉、声音问题数量、情感指数）。

**分析步骤**（五要素旅程图）：

1. **旅程结构**：将目标场景逐层分解为 **场景 → 行为 → 触点**（触点可按角色拆分，如用户触点 vs 柜员触点）。
2. **驱动因素**：用户侧（各行为下的核心需求与偏好，以"形容词+名词"表述，如"操作便捷流畅"，来自访谈/体验问题/工作坊）+ 产品侧（对应行为的业务目标）。每个行为只保留最重要的驱动因素。
3. **体验指标**：三类互补——主观态度类（ETS 分值、满意度评分）、行为交易类（操作时间、转化率、系统响应）、声音问题类（投诉量、各行为声音问题数、情感指数）。
4. **典型问题**：多渠道收集（体验管理平台、工单、访谈、可用性评估等）→ 筛选（须与驱动因素相关）→ 归类到具体行为/触点 → 按重要度分一/二/三级。
5. **优化点**：按优先级排序形成建议（关键触点一级问题 → 关键触点二级问题 → 非关键触点一级问题 → …）。
   - **关键触点识别**：体验指标数值低点 + 典型问题集中出现的触点 = 关键环节。
   - 有条件时做前后测（上线 ≥1 个月后同口径复测），输出指标变化值与前后问题数量对比。

**产出**：五要素旅程图 + 优化建议列表（按优先级）。

**综合要求**：**需要综合**（访谈 + ETS + 行为交易 + 用户声音四源）；访谈部分与主采集方式合并执行，通常无需单独大规模采集。

## 4. 服务蓝图

**定位**：服务流程分析产出框架（Shostack, 1982）。从服务提供者视角揭示"前台服务如何被后台支撑"，定位断点与优化点。

**激活条件**：研究类型为"竞品分析 / 体验测试（服务类产品）"；信号——服务流程、前后台衔接、断点、服务交付。产品存在线上线下结合的服务链路时尤为适用。

**数据依赖**：访谈（顾客体验与需求）+ 桌面研究 / 一线流程梳理（后台支撑与支持系统）。

**分析步骤**：

1. **确定服务阶段**：以顾客行为为主轴，把服务划分为若干阶段（如到店-办理-离店）。
2. **绘制四泳道**：顾客行为 / 前台员工行为（顾客可见）/ 后台员工行为（顾客不可见）/ 支持过程（系统与部门）。
3. **标注三条分界线**：互动线（顾客与前台之间）、可视线（前台与后台之间）、内部支持线（后台与支持系统之间）。
4. **标注有形展示**：可视线以上顾客能感知的实体证据（单据、界面、话术）。
5. **找断点/失败点**：用户等待、未知、抱怨集中的触点；衡量每步是否达标（等待时长、完成率等体验指标）。
6. **定义服务峰值**：结合峰终定律，规划"峰值体验点"并配置资源。

**产出**：服务蓝图 + 断点/优化点清单。

**综合要求**：**需要综合**（访谈 + 桌面/流程数据）；对"用户说了什么"与"后台如何支撑"两线做对照。

## 5. 心智模型

**定位**：信息架构分析产出框架（Indi Young）。把用户对功能/概念的认知方式结构化为"任务塔"，对比产品现有架构找出差距，导出信息架构建议。

**激活条件**：研究类型为"功能架构设计"；信号——功能如何分类、信息架构、导航结构、用户如何认知。

**数据依赖**：访谈（提取用户的任务陈述）+ 卡片分类（用户的分组逻辑与命名）。

**分析步骤**：

1. **提取任务**：从访谈中提取用户的"任务"陈述——用用户原话记录其想达成的事（动作 + 目的），剔除产品功能名和研究者概括。
2. **任务塔聚合**：将相似任务按相似性自下而上聚合为任务塔（每个塔一个用户视角的名称），形成心智模型图。
3. **对比现有架构**：将产品现有信息架构/功能组织与心智模型图逐项对照，找出"用户如何认知"与"产品如何组织"的差异（分类方式、命名术语、层级）。
4. **导出建议**：依据差异输出信息架构建议——分组、命名、层级、跨组归属调整。

**产出**：心智模型图（任务塔）+ 与现有架构差异分析 + 信息架构建议。

**综合要求**：**需要综合**（访谈任务提取 + 卡片分类结果）；卡片分类的分组一致性数据支撑任务塔的归组判断。

## 6. JTBD 动机映射（Jobs-to-Be-Done）

**定位**：需求动机分析框架（来源：Clayton Christensen、Tony Ulwick 的 JTBD 理论）。核心观点——用户不是"购买产品"，而是"雇用"产品来完成某项任务（get a job done），分析应聚焦任务与动机，而非产品功能本身。通过功能 / 情感 / 社会三个维度拆解任务动机、梳理任务完整生命周期、对照现状解决方案，定位"未被充分服务"的机会点。该框架重点回答"为什么用户会这样用 / 为什么会有这个需求"的深层动机问题，弥补卡诺模型只回答"需求优先级、不回答需求成因"的不足，与用户画像形成互补（画像回答"用户是谁"，JTBD 回答"用户在达成什么任务"）。

**激活条件**：研究类型为"用户需求分析 / 客群研究"；信号——动机、为什么、深层原因、未被满足的需求、用户现在用什么替代方案、任务视角、JTBD。

**数据依赖**：访谈（任务陈述与动机的主要来源，8-20 人）+ 问卷（量化验证动机维度分布与结果期望）+ 用户声音（原声佐证）。部分场景可叠加埋点（行为佐证"说了什么 vs 做了什么"）。

**分析步骤**：

1. **识别核心任务**：从访谈 / 用户声音中提取用户"本质上想达成什么"。用用户原话记录其想完成的任务，剔除产品功能名与研究者概括（任务提取原则同心智模型）。任务陈述句式：**当[情境]时，我想要[动机]，以便[期望结果]**。
2. **映射任务维度**：对每个核心任务拆解三个维度——
   - **功能性**：实际要完成的任务或产出成果（如"跨行转账"）
   - **情感性**：用户想要的感觉 / 想避免的感受（如"担心转错、希望安心"）
   - **社会性**：用户希望被他人如何看待（如"让家人觉得自己靠谱、被客户觉得专业"）
3. **定义任务阶段**：将任务展开为完整生命周期：**定义 → 寻找 → 准备 → 确认 → 执行 → 监控 → 调整 → 收尾**（define / locate / prepare / confirm / execute / monitor / modify / conclude），逐阶段记录用户做什么、用什么。
4. **识别结果期望**：为每个维度定义"成功长什么样"——成功标准、用户如何衡量、做到什么程度用户会满意 / 失望。
5. **映射现状解决方案**：用户当前如何"雇用"产品 / 方案来完成该任务——包括本产品、竞品、手工方法、不做（doing nothing）、雇人（hiring someone）、自行搭建（building internally）等替代方案。
6. **发现机会点**：逐阶段对照现状解决方案，找出"任务未被充分服务"的位置（未被满足的结果期望、未被覆盖的任务阶段、言行矛盾处），机会点须回落到可执行的改进方向。
7. **结构化呈现**：输出 JTBD 映射表（任务 / 情境 / 三维动机 / 任务阶段 / 结果期望 / 现状方案 / 机会点）+ 明确的设计启示（功能、运营、定位建议）。

**产出**：JTBD 动机映射表 + 机会点清单（含设计启示）。

**综合要求**：**需要综合**（访谈为主 + 问卷 / 声音佐证）；机会点置信度按 Step 4 三角验证五级定档标注（多源收敛 = 高/中高，单源 = 中高/中/中低/低，永不为"高"，见 `references/synthesis.md`「结论可信度五级定档」）。

## 使用约束

- 框架产出是**分析结论的可选模块**（对应 `references/analysis_template.md` 的可选模块），不强制每份分析结论都包含。
- 框架执行不新增招募与样本量，复用主采集方式数据（与研究方法侧原则一致）。
- 综合要求的判断：标"需要"的框架必须依托跨源综合执行（Step 4 阶段），数据不足时明确告知用户缺哪类数据，或降级为单源近似结论并标注。
- 同一研究可同时产出多个框架（如客群研究 + 需求分析 → 画像 + 卡诺；用户需求分析 → 画像 + JTBD 动机映射），框架间允许交叉引用（画像分群 → 卡诺分群差异、JTBD 任务维度差异）。
